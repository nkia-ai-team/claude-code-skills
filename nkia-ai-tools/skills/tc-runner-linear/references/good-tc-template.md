## 1. Redmine TC 의 표준 포맷

Redmine TC 는 4 개 섹션으로 구성된다. 각 섹션은 h3(`###`) 제목과 `~~~` 블록으로 감싼다.

```
### 사전조건
~~~
(TC 실행 전 충족되어야 하는 상태)
~~~

### 참고사항
~~~
(업무 규칙·UI 동작 힌트·선행 지식)
~~~

### 테스트절차
~~~
1. (첫 번째 동작)
2. (두 번째 동작)
...
~~~

### 예상결과 (캡처포함)
~~~
- (관찰 가능한 결과 1)
- (관찰 가능한 결과 2)
~~~
```

## 2. Good TC 체크리스트

본 계획서 `plans/tc-review-process.md` §4 "정비된 TC 기준" 과 일치한다. 모두 만족해야 인계 가능 상태.

### 2.1 구조 (A 축)

- [ ] **4 섹션 완전성** — 사전조건·참고사항·테스트절차·예상결과 모두 채워짐 (없으면 `없음` 명시)
- [ ] **절차 번호 연속성** — 1 부터 끊김 없이 연속
- [ ] **단일 UI 동작 단위** — 각 절차가 하나의 버튼 클릭·입력·확인 수준
- [ ] **예상결과 매핑** — 절차와 대응 관계 확인 가능

### 2.2 표현 (언어)

- [ ] **모호 부사 부재** — "정상", "문제없음", "올바르게", "제대로", "잘" 금지
- [ ] **관찰 가능한 서술** — 예상결과가 `{무엇이} {어디에} {어떻게} 표시/변경된다` 구조
- [ ] **현재 UI 용어 일치** — 메뉴·버튼·필드 레이블이 실제 EMS 와 동일
- [ ] **매뉴얼 근거 반영** — 업무 규칙·제약·자동동작은 매뉴얼(`ems-manual` 스킬)과 교차검증. 매뉴얼에 있는 규칙은 참고사항에 반영

### 2.3 원자성 (§5)

- [ ] **단일 검증 목적** — 하나의 TC = 하나의 기능/시나리오
- [ ] **독립 실행 가능** — 다른 TC 결과에 의존하지 않음
- [ ] **사전조건 일관성** — 테스트 중간에 전제가 바뀌지 않음

### 2.4 데이터 (§7)

- [ ] **장비·계정은 `tc-data/test_data.yaml` 키 참조** — 하드코딩·임의 사용 금지
- [ ] **운영 수치는 임의값 허용** — ping 시간·CPU % 등은 현실적 범위 내 임의로 서술 가능
- [ ] **재현 가능성** — 사전조건이 환경 구성으로 만들 수 있는 상태

## 3. 실제 예시 A — TC #110504 (CMM · 현재 팀에서 Good 으로 인정)

> 출처: <http://pims2.nkia.co.kr/issues/110504>
> 제목: `[CMM-01-10-01-03] 메뉴 추가 - URL 타입의 소메뉴 추가 - 대메뉴 신규 추가`
> 기능ID: `cmm-01-10-01`

### 3.1 본문 (원본)

```
### 사전조건
~~~
없음
~~~

### 참고사항
~~~
- 대메뉴를 신규 추가로 선택하면 하위 메뉴가 없으므로 중메뉴도 신규 추가가 자동으로 선택됩니다.
- 메뉴 타입이 URL로 등록되면 기능관리에 해당 메뉴의 기능이 자동으로 등록됩니다.
- 생성된 기능에 대한 권한이 할당되고 재로그인하면 등록한 메뉴가 표시됩니다.
- 대메뉴를 신규 추가로 선택한 경우, 타입 선택 드롭다운 없이 URL 필드가 바로 표시됩니다.
- 팝업 여부는 URL 타입일 때 자동으로 활성화(checked)되며 변경 불가(disabled)합니다.
~~~

### 테스트절차 (타입: URL, 레벨: 소메뉴 선택)
~~~
[메뉴 추가]
1. [운영관리] > 기본 설정 > [메뉴 관리] 메뉴를 선택합니다.
2. 상단의 [메뉴 추가] 버튼을 클릭합니다.
3. 레벨을 소메뉴로 선택합니다.
4. 대메뉴를 [신규 추가]로 선택합니다.
5. 대메뉴 아이콘을 선택합니다.
6. 대메뉴 이름을 입력합니다. (예: 엔키아)
7. 대메뉴 ID를 입력합니다. (예: NKIA) - 대문자와 _만 사용 가능
8. 중메뉴는 신규 추가가 자동 선택되어 있습니다.
9. 중메뉴 이름을 입력합니다. (예: 연구소)
10. 중메뉴 ID를 입력합니다. (예: RESEARCH_DEVELOP)
11. 소메뉴 이름을 입력합니다. (예: 연구4팀)
12. 소메뉴 ID를 입력합니다. (예: TEAM_BLOG)
13. 사용 여부 스위치를 활성화합니다.
14. 설명을 입력합니다.
15. URL을 입력합니다. (예: https://www.nkia.co.kr/)
16. 팝업 여부를 확인합니다. (자동 활성화, 변경 불가)
17. [저장] 버튼을 클릭하여 저장합니다.
18. 메뉴 새로 고침 확인 모달에서 [확인]을 클릭합니다.

[기능 관리 자동 등록 확인]
19. [운영관리] > 기본 설정 > [기능 관리]로 이동합니다.
20. 항목 컬럼 필터에 등록한 메뉴 이름을 입력하고 Enter를 누릅니다.
21. 등록한 메뉴가 기능 트리에 자동 등록되었는지 확인합니다.

[역할 권한 부여]
22. [운영관리] > 기본 설정 > [사용자 관리]로 이동하여 [역할] 탭을 클릭합니다.
23. Administrators 역할의 이름을 클릭합니다.
24. 기능 그리드에서 등록한 소메뉴의 조회 기능에 체크합니다.
25. [저장] 버튼을 클릭합니다.
26. 확인 모달에서 [확인]을 클릭합니다.

[재로그인 후 확인]
27. 로그아웃 후 재로그인합니다.
28. 사이드바에 등록한 대메뉴가 표시되는지 확인합니다.
29. 등록한 메뉴를 클릭하여 입력한 URL이 새 탭(팝업)으로 열리는지 확인합니다.
~~~

### 예상결과 (캡처포함)
~~~
- 메뉴가 목록에 등록됩니다.
- 메뉴와 관련된 기능이 기능관리에 자동 등록됩니다.
- 권한 할당 후 재로그인하면 사이드바에 메뉴가 표시되고, 선택 시 입력된 URL이 새 탭(팝업)으로 표시됩니다.
~~~

![](입력 내용 캡처)
![](메뉴관리에 등록된 결과 캡처)
![](기능관리에 자동으로 등록된 결과 캡처)
![](권한 할당 캡처)
![](로그인 후 메뉴 표시 및 선택 시 URL 팝업 캡처)
```

### 3.2 왜 Good 인가


| 좋은 점                         | 근거                                                      |
| ---------------------------- | ------------------------------------------------------- |
| **업무 흐름을 [라벨] 로 그룹화**        | 긴 TC 를 읽는 사람이 구조를 파악하기 쉬움                               |
| **참고사항이 풍부**                  | 업무 규칙·UI 자동동작·제약을 TC 읽는 사람이 미리 알 수 있음                    |
| **입력값 예시가 구체적**              | "예: 엔키아", "예: NKIA" 등으로 실행 재현성↑                         |
| **캡처 첨부로 시각적 검증 지원**         | 5 개 이미지로 각 단계 결과 확인 가능                                  |
| **제약 조건 명시**                 | "대문자와 _만 사용 가능", "자동 활성화, 변경 불가" 등 코드화 시 validation 힌트 |


### 3.3 본 프로세스 관점의 개선 여지 (원자화)

§5 원자화 규칙 관점에서 **분할 대상**이다. 29 단계가 한 TC 에 담겨 있으며 [라벨] 4 개가 이미 독립 검증 포인트임을 암시.

분할 시나리오 (예시):


| 분할 TC                                   | 범위       | 독립 실행? |
| --------------------------------------- | -------- | ------ |
| `cmm-01-10-01-03-01` 메뉴 추가 — 입력·저장       | 단계 1~18  | ✅      |
| `cmm-01-10-01-03-02` 기능관리 자동 등록 확인       | 단계 19~21 | ⚠️ 1 의존 |
| `cmm-01-10-01-03-03` 역할 권한 부여            | 단계 22~26 | ⚠️ 2 의존 |
| `cmm-01-10-01-03-04` 재로그인 후 메뉴 노출·팝업 확인 | 단계 27~29 | ⚠️ 3 의존 |


**분할 시 주의:** 2~4 는 1 의 결과물(등록된 메뉴)에 의존하므로 완전 독립 실행이 어렵다. 이 경우 두 가지 처리 옵션:

- **(a) 원본 유지 + 단일 큰 TC** — "엔드투엔드 워크플로우 검증" 으로 그대로 사용
- **(b) 분할 + 사전조건 연결** — 2/3/4 의 사전조건에 "1 의 결과가 등록된 상태" 를 명시

→ **이 판단은 `risk=high` 로 Claude 가 분할안을 제안만 하고 tgkim 결재** 에 넘긴다 (§5.3).

### 3.4 예상결과의 미세 개선 제안

원본 예상결과는 추상 수준이 다소 높다. **관찰 가능한 서술** 기준으로 다듬으면:

**원본:**
> 메뉴가 목록에 등록됩니다.

**개선안:**
> `운영관리 > 기본 설정 > 메뉴 관리` 그리드에 입력한 `대메뉴 이름(예: 엔키아) > 중메뉴 이름(예: 연구소) > 소메뉴 이름(예: 연구4팀)` 행이 추가되고, `URL` 컬럼에 입력한 URL 이 표시된다.

→ `selector + 기대값` 조합으로 검증 가능한 형태.

## 4. 실제 예시 B — SMS 단순 CRUD (Positive)

> 가상 예시 — 파일럿 이후 실제 SMS TC 로 대체 예정. 단일 기능 검증의 원자화 기준을 보여줌.

**제목:** `[SMS-01-02-01-001] 서버 목록 — UP 상태 서버 상세 조회`
**기능ID:** `sms-01-02-01`

```
### 사전조건
~~~
- `tc-data/test_data.yaml` 의 `sms.detail.hostname` 에 해당하는 서버가 EMS 에 등록되어 있으며 UP 상태.
- 조직 `MyOrganization` 의 `서버관리 > 서버목록` 메뉴 접근 권한을 가진 사용자로 로그인 완료.
~~~

### 참고사항
~~~
- 서버 상세는 하이브리드 레이아웃(우측 상세 영역, Drawer 아님).
- 서버 상태는 목록 "상태" 컬럼의 아이콘(`.suggested-check-circle-f` 계열)으로 표시.
~~~

### 테스트절차
~~~
1. 사이드바 하단 확장 버튼(`.st-first-menu-left-button-area`) 을 클릭하여 메뉴를 펼친다.
2. 사이드바에서 `서버관리 > 서버목록` 메뉴를 클릭한다.
3. 서버 목록 AG Grid 에서 `sms.detail.hostname` 에 해당하는 행을 클릭한다.
4. 우측 상세 영역의 `기본정보` 탭 내용이 표시되는지 확인한다.
~~~

### 예상결과
~~~
- 1. 사이드바 메뉴가 펼쳐져 `서버관리` 그룹이 노출된다.
- 2. 서버 목록 페이지로 이동하여 AG Grid(`div.ag-root`) 가 렌더링되고 행 1개 이상 표시된다.
- 3. 선택한 행이 하이라이트되고, 우측 상세 영역(`div.st-hybrid-detail`) 이 열린다.
- 4. 기본정보 탭의 `Hostname` 필드값이 `sms.detail.hostname` 과 일치하며, 상태 아이콘이 UP 으로 표시된다.
~~~
```

## 5. 실제 예시 C — Negative (쌍으로 작성 필수)

**제목:** `[SMS-01-02-01-002] 서버 목록 — 존재하지 않는 호스트명 검색 시 "결과 없음" 노출`
**기능ID:** `sms-01-02-01`

```
### 사전조건
~~~
- EMS 에 `__NOT_EXIST_<timestamp>__` 형태의 호스트명을 가진 서버가 존재하지 않음.
- `MyOrganization` 의 `서버관리 > 서버목록` 메뉴 접근 권한을 가진 사용자로 로그인 완료.
~~~

### 참고사항
~~~
- "결과 없음" 은 AG Grid 의 `ag-overlay-no-rows-wrapper` 오버레이로 표시된다.
~~~

### 테스트절차
~~~
1. 사이드바를 펼치고 `서버관리 > 서버목록` 으로 이동한다.
2. Hostname 컬럼 필터 입력창에 `__NOT_EXIST_<timestamp>__` 를 입력한다.
3. 엔터 키를 입력하여 필터를 적용한다.
~~~

### 예상결과
~~~
- 1. 서버 목록 페이지가 열리고 AG Grid 가 렌더링된다.
- 2. 필터 입력창에 입력 문자열이 반영된다.
- 3. 그리드 본문이 빈 상태로 전환되고 `ag-overlay-no-rows-wrapper` 오버레이에 "검색 결과가 없습니다" 문구가 노출된다.
~~~
```

## 6. Bad → Good 대비 (흔한 오염 유형)

정비 시 Claude 가 자동 교정을 제안하는 전형적 패턴.


| Bad (흔한 오염)                   | 위반 축      | Good (교정 후)                                             |
| ------------------------------ | --------- | ------------------------------------------------------- |
| 절차: "서버를 등록하고 결과를 확인한다"        | A4 (다단계 뭉침) | "등록 버튼 클릭" / "목록에서 신규 행 노출 확인" 두 절차로 분리                |
| 예상결과: "정상 동작한다"               | A3 (모호)   | "상태 아이콘이 UP 으로 표시된다"                                    |
| 사전조건: "테스트 환경이 준비됨"           | 재현 불가     | "`sms.detail.hostname` 서버가 UP 상태로 등록되어 있음"              |
| 절차: "검색한다"                    | B3 (불분명)  | "Hostname 컬럼 필터에 X 를 입력하고 엔터"                           |
| 메뉴명: "서버 관리 > 목록 조회"          | B2 (UI 불일치) | "서버관리 > 서버목록" (실제 레이블)                                  |
| 예상결과: "화면이 뜬다"                | B4 (관찰 불가) | "`div.st-hybrid-detail` 영역에 기본정보 탭이 노출된다"               |
| 절차 번호: 1, 2, 3, 5, 6           | A2 (끊김)   | 연속 번호로 수정                                                |
| 사전조건: "Positive 테스트 통과 후"     | 독립 실행 불가  | fixture·데이터로 독립 재현 가능한 상태 서술                             |
| 절차에 하드코딩: `192.168.213.200`   | 7.1 위반    | `tc-data/test_data.yaml` 의 `sms.detail.hostname` 참조     |

## 8. 참고사항 작성 가이드 + 매뉴얼 교차검증

**참고사항은 쓰레기통이 아니다.** 다음 3가지에 해당하는 내용만 넣는다.

- **UI 동작 규칙** — 자동 선택·자동 활성화·비활성화 조건 (TC #110504 의 "중메뉴 자동 선택" 등)
- **업무 규칙** — 입력 제약 ("대문자와 _만 사용 가능"), 후처리 ("기능관리에 자동 등록")
- **화면 구조 힌트** — "Drawer 가 아닌 하이브리드 레이아웃", "선택 행 하이라이트" 등

→ 자동화 코드화 단계에서 **테스트 데이터 제약·어설션 조건의 근거**로 직접 사용되므로 정확하게 작성.

### 8.1 매뉴얼 교차검증 (`ems-manual` 스킬 활용)

참고사항·예상결과·사전조건을 정비할 때 **매뉴얼을 반드시 교차 참조**한다. 계획서 `plans/tc-review-process.md` §2.1 원칙에 따라 "현재 UI + 매뉴얼 교차검증" 이 정비 기간의 임시 기준이다.


| 참조 상황                           | 매뉴얼 활용 방식                                                  |
| ------------------------------- | --------------------------------------------------------- |
| UI 에서 관찰한 동작의 **의도 확인**         | 매뉴얼에서 해당 기능 섹션 읽고 자동동작·제약 여부 확인                             |
| 참고사항의 **업무 규칙 근거 확보**           | 매뉴얼 인용 가능하면 "(매뉴얼 §X.Y)" 출처 표기                              |
| 예상결과의 **숨은 결과(자동 후처리) 추가**      | UI 로 즉시 보이지 않는 후처리(예: "기능관리에 자동 등록") 는 매뉴얼에서 확인 후 예상결과에 포함 |
| **UI 와 매뉴얼 불일치 발견 시**           | 정비 보류 + 제품 버그 의심 플래그 (§2.1). tgkim 결재 큐로 에스컬레이션            |


### 8.2 TC #110504 의 참고사항이 왜 잘 쓰여있나

아래 5 항목은 매뉴얼 기반 업무 규칙·UI 자동동작이 집약된 사례이다.

- "대메뉴를 신규 추가로 선택하면 하위 메뉴가 없으므로 중메뉴도 신규 추가가 자동으로 선택" → **UI 자동동작**
- "메뉴 타입이 URL로 등록되면 기능관리에 해당 메뉴의 기능이 자동으로 등록" → **숨은 후처리** (§8.1 의 세번째 행)
- "생성된 기능에 대한 권한이 할당되고 재로그인하면 등록한 메뉴가 표시" → **업무 흐름 규칙**
- "대메뉴를 신규 추가로 선택한 경우, 타입 선택 드롭다운 없이 URL 필드가 바로 표시" → **조건부 UI**
- "팝업 여부는 URL 타입일 때 자동으로 활성화(checked)되며 변경 불가(disabled)" → **입력 제약**

→ 모두 **매뉴얼 또는 개발자 완료 리뷰에서만 알 수 있는 정보**. UI 만으로는 놓치기 쉬움. 정비 시 매뉴얼 교차 없이 참고사항을 채우면 이 수준에 도달할 수 없다.

### 8.3 매뉴얼 참조가 막힐 때

- **해당 기능의 매뉴얼 항목 자체가 없음** (신규 기능 등) — UI 관찰만으로 작성하되 참고사항에 "매뉴얼 미존재" 명시, Decision Log 에 플래그
- **매뉴얼이 낡음** (UI 와 명백히 다른 기술) — UI 우선, 매뉴얼 불일치는 매뉴얼 갱신 큐로 분리 (본 프로세스 외)
- **매뉴얼 권한 부재** — `ems-manual` 스킬 호출 실패 시 tgkim 에게 확인 요청

## 9. 인계 기준 (다른 팀 코드화를 위한 TC)

정비된 TC 가 **다음 팀이 자동화 코드로 변환 가능** 한 상태로 보기 위한 최종 체크.

- [ ] §2 체크리스트 4 개 축 모두 통과
- [ ] 절차 번호 ↔ 예상결과 번호 1:1 대응 (또는 N:M 명시)
- [ ] 각 예상결과가 **selector + 기대값** 조합으로 어설션 가능
- [ ] 사전조건이 `test_data.yaml` 또는 fixture 로 매핑 가능
- [ ] 원자화 판단 완료 (분할됐거나 분할 불필요 이유 기록)
- [ ] 캡처 이미지가 있다면 현재 UI 와 일치

인계 시점에 이 체크를 통과한 TC 목록을 다른 팀에 전달.
