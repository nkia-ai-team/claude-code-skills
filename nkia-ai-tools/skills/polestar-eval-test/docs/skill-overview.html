polestar-eval-test

폴스타 AI (chat-ai) 가 사용자 발화에 mongo 모니터링 데이터를 잘 가져와 UI 에 답하는지를 — chrome 자동화로 직접 던지고, 답을 본 다음, 점수로 채점하는 skill. 외부 framework (Grafana o11y-bench / Splunk SAIA 등) 조사 결과, 우리가 차용한 패턴, 실제 돌렸을 때 나온 보고서까지 한 페이지 안내.

1. 이 skill 이 뭐 하는 건가

쉽게: 사람이 chat-ai 에 들어가서 "서버 부하 보여줘" 같은 질문을 던지고 답이 맞는지 손으로 확인하던 작업을, 사람 없이 자동으로 돌리는 도구.
🎯 평가 대상
chat-ai 의 UI 응답
Polestar 의 chat-ai 가 mongo 모니터링 데이터를 조회하고 chrome 의 chat UI 에 답을 그려주는 전체 chain.
📐 평가 scope
답변 품질만
"사용자가 물었을 때 잘 답하는지" 만 본다. 실제 장애 주입, RCA workflow, trace 따라가기는 안 함.
🤖 자동화
풀자동
Challenger / Verifier 는 LLM subagent. Runner 는 chrome API 직접 호출 (UI 의 React 우회).
📊 산출물
report.md + 이미지
사용자가 한 파일만 보고 evidence 확인 가능 — 이번 페이지의 §8 보고서 예시 참고.

3. 우리는 무엇이 같고 다른가

외부 framework 들과 우리의 핵심 차이는 — chrome UI 자체를 평가 대상으로 본다 는 것. 다른 모두는 agent ↔ query 언어 (PromQL/SPL/KQL) 까지만 평가.

3.1 무엇이 같나 (3 패턴 차용)

① deterministic + rubric 2-tier 채점

출처: o11y-bench

코드/로그로 자동 채점되는 5축 (Tier A, 75점) + LLM/vision 이 판단하는 2축 (Tier B, 25점) 명시 분리.

왜: LLM 의 응답 변동에 영향 안 받는 회귀 감지 가능. screenshot 없는 케이스도 Tier A 만으로 verdict.

② N attempts + 분산 측정

출처: o11y-bench (3 attempts default)

--attempts=3 으로 같은 query 3 회 → median + 표준편차. LLM stochasticity + live mongo 데이터 변동 둘 다 흡수.

왜: scenario_time.txt 같은 시간 고정은 우리 live polestar 에선 불가능 (실시간 데이터).

③ task-spec → tasks 분리

출처: o11y-bench

scenarios/<cat>.yaml = source of truth → runs/<run-id>/queries.json = Challenger expanded output.

우리 구조와 이미 동치. 명시만 추가.

3.2 무엇이 다르나 (차용 안 한 6 가지)

❌ AIOpsLab fault injection
scope 초과 우리는 mongo 조회 답변만 봄. RCA workflow 는 평가 대상 X.
❌ Harbor agent runtime
architecture 충돌 우리는 chrome UI 자체 평가. agent runtime 도입은 X.
❌ scenario_time.txt
불가능 polestar mongo 는 실시간 데이터. 시간 고정 불가.
❌ 공개 leaderboard
내부 product 회귀 검증이라 외부 노출 X.
❌ AGPL v3 코드
라이선스 o11y-bench / AIOpsLab 패턴만 차용, 코드 X (전염 방지).
❌ Datadog noise 주입
자연 포함 우리는 production polestar 직접 평가 → noise 자동.

4. skill 동작 6 단계

매 단계 진입 시 TaskCreate / TaskUpdate 로 사용자에게 실시간 가시화 — 침묵하지 않는다.
1
Setup
target / login / 건수 / 병렬도 결정
2
Memory
사용자 메모리 snapshot
3
Challenger
subagent 가 query 생성
4
Runner
chrome 으로 send + 캡쳐
5
Verifier
subagent 가 채점
6
Report
markdown + 이미지 산출

각 단계 무엇을 하는가

1. Setup — 사용자에게 묻고 정한다:
  • target — 개발 104 / 운영 57
  • 로그인 방식 — 사용자 직접 / 자동 fill
  • scenario — 단일 카테고리 (예: cross-domain) 또는 all
  • 테스트 건수 — 카테고리당 3/5/10 또는 직접
  • 병렬 send — 1 / 2 / 4 / 직접 (default 1, 권장 4)
  • attempts — 1 / 3 / 직접 (default 1)
인자 없이 호출하면 4 단계 다 물어봄.
2. Memory snapshot — 사용자의 메모리 상태를 dump.
  • Stage A: POST /api/chat-ap/memories/list + setting/get (정상 path)
  • Stage B: API errorCode (예: POLESTAR_00102) 시 UI 페이지 navigate + DOM snapshot fallback
  • Stage C: 둘 다 실패 시 {enabled:null, items:[]} 로 graceful 진행
Verifier 가 이 snapshot 의 item 들이 응답에 반영됐는지 판단할 때 ground truth 로 씀.
3. Challenger (subagent) — 카테고리 별로 LLM subagent 한 명씩 spawn. 각 agent 가 scenarios/<cat>.yaml seed + 메모리 snapshot + Polestar 도메인 reference 입력 받아서 한국어 query N 개 expand.
산출: queries.json — 각 entry 가 {id, query, difficulty, expected}.
4. Runner — query 별로:
  1. evaluate_script 안에서 POST /api/chat-ap/conversation + SSE reader.read() until done (React onClick 우회, 100% 도달)
  2. send 도달 검증 (docker log MainStream] 시작 grep)
  3. chrome 을 conversationId 페이지로 navigate → wait_for 키워드 → screenshot
  4. docker log capture (target=104 만)
  5. checkpoint: runs/<run-id>/<idx>-<qid>.json 즉시 저장. 세션 끊겨도 --resume 으로 재실행 가능
병렬 send 옵션 (--parallel-send=4) 사용 시 query N 개를 Promise.all 로 동시 발사, screenshot 만 sequential.
5. Verifier (subagent) — Challenger 처럼 카테고리 별 subagent. 입력: queries.json + 각 query 의 result file + screenshot + log + memory snapshot. 7 축 (Tier A 5 + Tier B 2) 채점. screenshot 은 Read tool 로 PNG 직접 열어서 Claude vision 으로 table column 수 / 그래프 등 분석. 산출: verifier-results.json.
6. Report — report.md 작성. 메모리 사전 점검 + 시나리오 별 (query / 응답 / 평가표 / verdict 사유) + 카테고리 요약 + 발견 이슈 + 권장 후속. screenshot 은 markdown ![](./...) inline embed — 사용자가 한 파일만 보면 됨.

5. 시나리오 카테고리 11 개 — 도메인 기반

6. Challenger 페르소나 — 현실적 발화

핵심: query 시드를 chat-ai 내부 도메인명 / metric 정확명까지 아는 사람이 만들면 안 됨. 실제 SRE/AIOps 담당자는 "자기 직무 + IT 일반 용어" 만 알고 chat-ai 의 tool / field 명은 모름.
✅ 사용자가 아는 것
  • 자기 직무 — 장애 대응 / 알람 처리 / 부하 추적 / 변경요청
  • IT 일반 용어 — OOM, Lock, Active session, p99, 트랜잭션
  • 자기 환경의 일부 hostname / 서비스 명 — "운영 서버", "결제 DB" 같은 약칭
❌ 사용자가 모르는 것
  • Polestar 내부 도메인명 — SMS, DPM, APM 같은 약어
  • 정확한 metric field 명 — cpu_utilization, disk_avg_io
  • chat-ai 의 tool 명 — query_sms_servers 등
  • 시스템 내부 메커니즘 — Phase B, verifier_node 등

발화 분포 (강제)

수준비율예시chat-ai 검증 가치
모호 (vague) 30% "서버 좀 느린데?", "DB 죽었나?", "사용자 불만 폭주", "어제 무슨 일?" routing / intent 추출 robustness
메트릭 인지 (semi-tech) 40% "CPU 부하 높은 서버", "메모리 꽉 찬 데", "응답시간 느린 서비스" field 매핑 + tool 선택
정확 발화 (tech) 30% "CPU 80% 넘는 서버", "p99 응답시간 1초 넘는 서비스" argument 정확성
왜 모호 발화도 평가?
  • 실제 사용자가 처음 도구 만났을 때 자연스러운 발화 패턴 검증
  • chat-ai 가 "어떤 서버요?" 같은 합리적 반문 시 PARTIAL (무한 반문 시 FAIL)
  • 베테랑 발화만 평가하면 routing 회귀 못 잡음

메모리 drift 추적 (before / after / diff)

chat-ai 의 MemoryExtract 가 매 turn 끝에 자동 메모리 추출 시도. 평가 query 가 사실 발화 ("X 는 109번이야 기억해") 면 새 메모리 자동 추가 → baseline drift.
  • run 시작 시 memory-snapshot-before.json dump (Verifier baseline)
  • run 끝나면 memory-snapshot-after.json dump
  • memory-snapshot-diff.json = run 도중 추가된 / 삭제된 / 변경된 item
  • Verifier 의 memory 축은 baseline (before) 만 평가 — drift 영향 X

7. 평가 7 축 — 자동 + LLM 판단

o11y-bench 의 패턴 차용. 자동 채점되는 부분과 LLM 이 판단하는 부분을 명시 분리. 자동 부분만으로도 회귀 감지 가능 (LLM 변동 영향 X).

deterministic 5 축

코드 / 로그 / 응답 텍스트 grep 으로 자동 채점. LLM 변동에 영향 받지 않아 회귀 감지에 적합.

9.1 시드 보강

  • wpm / kcm / nms — 현재 각 5 seed. dev 데이터 부재라 expand 어려움. 하지만 graceful "데이터 없음" 응답 검증 가치는 큼.
  • alarm / itg — 시간 표현 / severity 다양성 / 변경요청 form 종류 보강 (각 3~5 seed 추가)
  • cross-domain — 현재 SMS-only cross-tier. APM+DPM / DPM+SMS / alarm+SMS 같은 multi-도메인 cross-tier seed 추가 (3 seed)
  • 모호 발화 (vague) 비율 30% 강제 — Challenger 가 정확 발화로 치우치지 않게. 각 도메인 yaml 의 expand_hints 에 페르소나 안내 추가

9.2 회귀 fix

  1. Phase B prior 전달 — task 1 결과 0건 case 의 task 2 graceful fallback
  2. Phase C / Layer 3 — metric_keys 단일 변환 case 의 agent prompt tuning
  3. chat-ai 의 memory hint → tool args mapping 도입 (Phase B 의 Layer 3 와 유사)
  4. chat-ap history rendering metric 누락 (별개 버그)
  5. verifier_node placeholder substitution leak (별개 버그)
