## 0. 운영 구조 — Project > Feature > Task

업무는 항상 다음 3계층으로 구성합니다. (v1.3)

| 구분 | 의미 | Linear 매핑 |
|------|------|------------|
| **Project** | 일정과 목표가 있는 실행 묶음 (분기 단위) | Linear Project |
| **Feature** | 실제 사용자가 체감하는 기능 | Linear Issue (Feature 타입) |
| **Task** | Feature를 만들기 위한 세부 작업 | Linear Sub-issue (Task 타입) |

**예시:**

    Project: 2026 Q2 AI Portal 고도화
      Feature: 알람 분석 결과 요약                ← Linear Issue
        Task: 알람 상세 API 확인                  ← Sub-issue
        Task: AI 요약 프롬프트 작성               ← Sub-issue
        Task: 결과 카드 UI 개발                   ← Sub-issue

### 0.1 작성 분리 원칙

| 위치 | 작성 수준 |
|------|---------|
| **구글시트** | Project / Feature 단위 간단 PRD + 전체 현황판. 컬럼: Project / Feature / 목적 / 주요 내용 / 범위 / 완료 기준 요약 / 담당·상태 / Linear 링크 |
| **Linear Feature 이슈** | 상세 완료 조건(체크리스트), 하위 Task |
| **Linear Sub-issue (Task)** | 작업 내용 + 간단 완료 조건만 |

### 0.2 용어 매핑 (AC / DoD ↔ 가이드라인)

| 가이드라인 표현 | 의미 |
|----------------|------|
| 완료 기준 요약 (구글시트) | Feature AC 요약 1줄 |
| 상세 완료 조건 (Linear Feature) | Feature AC + DoD 체크리스트 |
| 완료 조건 (Linear Task) | 세부 작업 완료 여부 |

### 0.3 Feature 등록 기준 (백로그)

1. 아이디어 수준의 문장은 Feature로 등록하지 않는다.
2. Feature는 사용자가 체감할 수 있는 기능 단위로 작성한다.
3. 완료 기준 요약이 없으면 Cycle 대상에 넣지 않는다.
4. 담당자가 없는 Feature는 진행 대상으로 보지 않는다.

| 나쁜 Feature | 좋은 Feature |
|-------------|------------|
| AI 알람 분석 고도화 | 알람 분석 결과 요약 / 알람 권장 조치 생성 / 알람 분석 근거 데이터 표시 |

## 1. 이슈 상태

| 상태 | 정의 | 비고 |
|------|------|------|
| **Backlog** | 해야 하지만, 이번 사이클은 아닌 일 | 쓰레기통이 아님. 순서만 뒤인 필수 업무 |
| **Todo** | 이번 사이클에 착수할 준비 완료 | - |
| **In Progress** | 실제로 손을 대고 있는 상태 | 회의만 하고 코드를 안 짰으면 Todo |
| **In Review** | AC + AI 검증을 충족하여 리뷰 대기 중 | validator 검증 통과 후 자동 이동 |
| **Done** | 사람의 최종 확인까지 완료된 상태 | In Review → 사람 확인 → Done |
| **Canceled** | 안 하기로 결정된 일 | "왜 안 하는지" 댓글로 자산화 |

**금지 사항:**
- **QA / Deploying 등 별도 상태 금지** — 리뷰가 필요한 작업은 In Review 상태 사용
- **In Progress 3일 이상 방치 금지** — 이슈를 쪼개거나 도움을 요청

## 2. Estimate

피보나치 스케일 (1, 2, 3, 5, 8, 13, 21)을 사용합니다. **시간 단위로 쓰지 마세요.**

| 포인트 | 의미 | 예시 | 착수 절차 |
|--------|------|------|----------|
| **1** | 생각 없이 바로 처리 | 설정값 변경, 오타 수정 | 바로 착수 |
| **2** | 반나절이면 끝남 | 단순 버그 수정, API 필드 추가 | 바로 착수 |
| **3** | 하루 정도 집중 필요 | 엔드포인트 하나 개발, 문서 작성 | **이슈명 `[AC 요청]` + 팀장 승인** |
| **5** | 2~3일, 약간의 불확실성 | 새 기능 구현, 리팩토링 | **이슈명 `[AC 요청]` + 팀장 승인** |
| **8** | 일주일급, 불확실성 있음 | 아키텍처 변경, 새 서비스 연동 | **이슈명 `[AC 요청]` + 팀장 승인** |
| **13+** | 너무 큼 | - | **반드시 하위 이슈로 분해** |

## 4. AC 검토 — 이슈명 접미사 컨벤션

Estimate 3 이상 이슈는 이슈명 끝에 접미사를 붙여 AC 검토 상태를 표시합니다.

| 접미사 | 의미 | 누가 붙이나 |
|--------|------|------------|
| _(없음)_ | AC 미작성 | - |
| `[AC 요청]` | AC 작성 완료, 팀장 검토 요청 | **팀원** |
| `[AC 확인]` | 팀장 검토 완료, 착수 가능 | **팀장** |

- 착수 후에도 접미사 `[AC 확인]`은 제거하지 않고 유지 (이력 추적 용도)

## 6. 공통 AC 항목

작업 유형에 따라 AC에 **공통 섹션**을 추가합니다.

### 6.1 코드 변경 작업

코드 변경이 포함된 작업(새로운 기능 개발, 기능 개선, 리팩토링, 버그 수정 등):

    ### 공통
    - [ ] 코드 리뷰 완료 → 이슈 리소스에 PR/MR 링크 첨부

**적용 규칙:**
- PR/MR이 필요한 작업에만 추가 (리서치, 평가 등 코드 변경 없는 작업은 제외)
- AC 항목 본문에 `→ 결과물: PR 링크 {{pr_link}}`를 넣지 않음
- PR/MR 링크는 이슈 리소스(links)로 첨부됨 → evidence 스킬이 `save_issue`의 `links` 필드로 추가
- validator는 이슈 `attachments`에서 PR/MR URL을 확인하여 검증

### 6.2 문서 작업 (단일 문서)

한 페이지에 여러 섹션을 작성하는 문서 작업:

    ### 공통
    - [ ] 최종 게시 완료 → 결과물: 게시된 문서 URL {{published_url}}

**적용 규칙:**
- 모든 AC가 같은 문서를 대상으로 할 때만 적용
- 개별 AC 항목에 `→ 결과물: 문서 링크`를 넣지 않음
- 다중 문서인 경우 공통 항목 대신 각 AC에 개별 문서 링크 첨부

## 7. AI-Verification Loop

### Estimate별 분기

- **Estimate 1~2**: AC 작성 → 바로 개발 착수
- **Estimate 3+**: AC 작성 + `[AC 요청]` → 팀장 AC 승인 (Gate 1) → 개발

### 검증 단계

| 단계 | 내용 | 검증 주체 |
|------|------|----------|
| **1단계** | 이슈 및 AC 정의 | 사람 + AI |
| **2단계** | 개발 및 PR — 코드 스타일, 보안, 성능, 테스트 | AI Code Reviewer |
| **3단계** | AC 검증 — PR 구현이 AC를 빠짐없이 충족하는지 대조 | Linear Validator Agent |
| **4단계** | Self-Merge — 2단계 + 3단계 통과 시 개발자가 즉시 머지 | 개발자 |

## 8. Health 판단 기준

Status Update의 Health(On Track / At Risk / Off Track)를 판단하는 기준입니다. 자동 제안은 참고용이며, **사용자가 최종 결정**합니다.

### 8.1 프로젝트 Health (Project Update)

| Health | 정의 | 시그널 |
|--------|------|--------|
| **On Track** | 계획대로 진행 중 | Done 이슈 증가, 신규 블로커 없음, 이전 계획 대비 정상 진행 |
| **At Risk** | 일부 리스크 존재하나 대응 가능 | 블로커 1건, In Progress 3일+ 방치 이슈 존재, 이전 "다음 주 계획" 미달성 항목 존재 |
| **Off Track** | 심각한 지연 또는 차질 | Done 이슈 0건(활동 없음), 블로커 2건+ 미해결, 핵심 마일스톤 지연 |

**자동 판단 로직:**
1. Off Track 시그널 1개 이상 → Off Track 제안
2. At Risk 시그널 1개 이상 → At Risk 제안
3. 나머지 → On Track 제안

### 8.2 이니셔티브 Health (Initiative Update)

| Health | 정의 | 시그널 |
|--------|------|--------|
| **On Track** | 모든 소속 프로젝트가 On Track | 전체 프로젝트 On Track |
| **At Risk** | At Risk 프로젝트 1건 이상 | 최소 1개 프로젝트가 At Risk (Off Track 없음) |
| **Off Track** | Off Track 프로젝트 1건 이상 | 최소 1개 프로젝트가 Off Track |

**자동 판단 로직:**
- Worst-case 집계: 소속 프로젝트 중 가장 나쁜 Health를 이니셔티브 Health로 제안
- 프로젝트 업데이트가 없는 프로젝트는 "업데이트 없음"으로 표시하고 At Risk 신호로 간주

## 9. Cycle 운영 방식 (v1.3)

Cycle은 **2주 단위** 실행 단위입니다.

### 9.1 Cycle Planning (시작 시)

확정 항목:

1. 이번 Cycle 대상 Feature
2. Feature Owner
3. 구글시트 간단 PRD 작성 여부
4. Linear 등록 여부
5. Linear 상세 완료 조건 작성 여부

### 9.2 Mid Check (중간)

3가지만 확인:

1. 이번 Cycle 안에 끝낼 수 있는가?
2. 막힌 이슈가 있는가?
3. 범위를 줄이거나 조정해야 하는가?

### 9.3 Cycle 완료 리뷰

**Done 처리된 Feature만** 리뷰. 진행 중인 백로그 전체는 보지 않습니다.

**확인 기준:**
1. 구글시트의 완료 기준 요약을 만족했는가?
2. Linear의 상세 완료 조건을 만족했는가?
3. 실제 화면/API/결과물로 확인 가능한가?

**Feature별 진행 순서:**

| 순서 | 내용 |
|------|------|
| 1 | 이번 Cycle에서 완료하려던 범위 확인 |
| 2 | 실제 결과물 또는 화면 확인 |
| 3 | 완료 기준 요약 충족 여부 확인 |
| 4 | Linear 상세 완료 조건 체크 |
| 5 | 남은 이슈 여부 확인 |
| 6 | Done / 보완 필요 / 이월 / Blocked 판정 |

### 9.4 Cycle 완료 판정 4종

| 판정 | 의미 | 후속 |
|------|------|------|
| **Done** | 완료 기준 + 상세 완료 조건 + 실제 결과물 모두 충족 | 완료 처리 |
| **보완 필요** | 일부 미흡, 동일 Cycle 내 마무리 가능 | 후속 Task로 분리 |
| **이월** | 다음 Cycle로 넘김 | 다음 Cycle 후보 |
| **Blocked** | 외부 의존/리소스 부족 등으로 진행 불가 | 사유와 담당자 기록 |

### 9.5 사이클 중간 투입 금지

이미 시작된 사이클에 이슈를 새로 투입할 때:

1. **원칙적으로 금지** — 기존 이슈 1개를 빼야 함 (Trade-off)
2. Backlog 또는 다음 사이클에 배치를 권장
3. 긴급한 경우에만 현재 사이클에 투입 (**사유 기록 필수**)

## 10. 완료 인정 기준 — 산출물 표 (v1.3)

Feature가 Done으로 인정되려면 아래 기준을 **모두** 만족해야 합니다.

| 확인 항목 | 기준 |
|----------|------|
| 완료 기준 요약 충족 | 구글시트에 적은 완료 기준을 만족해야 함 |
| 상세 완료 조건 충족 | Linear Feature 이슈의 체크리스트가 충족되어야 함 |
| 결과 확인 가능 | 화면, API, 파일, 로그 등으로 결과를 확인할 수 있어야 함 |
| 기본 테스트 완료 | 주요 사용 시나리오 기준으로 테스트가 완료되어야 함 |
| 남은 작업 정리 | 미완료 항목은 후속 Task로 분리되어야 함 |
| 상태 갱신 | 구글시트와 Linear 상태가 갱신되어야 함 |

### 10.1 기능 유형별 보여줘야 할 산출물

"했습니다"라는 설명만으로는 인정되지 않습니다. 다음 중 해당 유형에 맞는 산출물을 제시해야 합니다.

| 기능 유형 | 리뷰 시 보여줄 것 |
|----------|-----------------|
| 화면 기능 | 실제 화면 또는 캡처 |
| API 기능 | API 호출 결과, 응답 예시 |
| AI 분석 기능 | 입력 예시, AI 출력 결과, 화면 반영 결과 |
| 데이터 조회 기능 | 조회 조건, 조회 결과, 샘플 데이터 |
| 보고서 기능 | 생성된 보고서 화면 또는 파일 |
| 설정 기능 | 설정 전/후 화면, 저장 결과 |
| 문서/기획 기능 | 작성된 문서, 확정된 항목, 리뷰 결과 |

### 10.2 증빙 원칙

- **금지**: `코드 변경`, `git diff`, `구현 완료`, `수정 완료` — 동작 증명이 아님
- **허용**: 실제 실행 결과 (테스트 출력, 로그, 스크린샷, API 응답, DB 쿼리 결과, 메트릭, CI/CD 로그, 네트워크 캡처, 데이터 경로 + 건수)

## 11. 역할 정의 (v1.3)

### 11.1 팀장

방향과 우선순위를 정한다.

- 이번 분기/Cycle에서 중요한 Feature를 정한다.
- Feature Owner를 지정한다.
- 우선순위 변경, Hold, Drop 등 주요 의사결정을 한다.

### 11.2 스프린트 마스터

Cycle이 정상 작동하게 관리한다.

- Cycle Planning, Mid Check, Review가 진행되게 한다.
- Linear의 Feature, Task, Cycle 상태가 정리되어 있는지 확인한다.
- 막힌 이슈가 방치되지 않게 확인한다.
- Review 결과와 후속 Task를 기록한다.
- Cycle 시작/종료 공지를 작성·공유한다 (§5.5, §5.6).

### 11.3 Feature Owner

해당 Feature가 끝까지 완료되도록 책임진다.

- Feature의 목적, 주요 내용, 범위를 정리한다.
- 구글시트에 완료 기준 요약을 작성한다.
- Linear에 상세 완료 조건과 하위 Task를 만든다.
- Cycle Review에서 결과와 완료 기준 충족 여부를 설명한다.
- 남은 작업은 후속 Task로 분리한다.

### 11.4 개발 담당자

할당된 Task를 수행하고 결과물을 제공한다.

- 맡은 Task를 수행한다.
- Linear 상태를 최신으로 유지한다.
- API, 데이터, 일정, 기술 이슈를 빠르게 공유한다.
- 화면/API/로그/테스트 결과 등 확인 가능한 산출물을 제공한다.
